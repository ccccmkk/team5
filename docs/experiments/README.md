# 검증 기록

과제 평가 기준은 완성도가 아니라 **문제정의 → 가설 → 제작 → 데이터 검증 → 재가설**을 반복한
과정이다. 그 반복의 증거가 이 폴더다.

주 1회, `YYYY-MM-DD-N차-검증.md` 형식으로 한 장씩 쌓는다. 숫자가 좋든 나쁘든 적는다.
**가설이 틀렸다는 기록이 맞았다는 기록보다 점수에 유리하다.** 틀린 걸 발견하고 바꿨다는 게
반복의 증거이기 때문이다.

## 측정하는 가설

| # | 가설 | KPI | 성공 기준 |
|---|---|---|---|
| H1 | 사람들은 자기 몸 정보를 입력해준다 | `profile_complete` / `profile_start` | 60% |
| H2 | 선택 항목까지 입력할 의향이 있다 | `profile_complete`의 `optional_field_count` ≥ 1 비율 | 30% |
| H3 | 유사도 정렬이 실제로 도움이 된다 | `view_model`을 `has_profile`로 나눈 평균 체류시간 비교 | 프로필 보유자가 더 김 |
| H4 | 조회만 하지 않고 기여도 한다 | `review_submit` / `review_start` | 15% |
| H5 | 추천을 신뢰해 실제 구매로 넘어간다 | `outbound_click` / `view_recommendation` | 25% |

**표본이 얇을 때는 H5를 먼저 본다.** 초기 트래픽이 수십 명이면 H4는 읽히지 않는다.
분모가 20인데 한 명 차이로 5%p가 움직이면 그건 신호가 아니라 잡음이다.
링크 클릭은 허들이 낮아 같은 표본에서도 비율이 덜 흔들린다.

`empty_state_shown`의 `reason` 분포도 함께 본다. 어떤 빈 화면이 자주 뜨는지가
다음에 고칠 지점을 알려준다.

## 숫자 보는 곳

GA4 > 보고서 > 참여도 > 이벤트. 위 이벤트 이름으로 검색한다.
정의는 [스펙 §15](../superpowers/specs/2026-08-12-levis-fit-service-design.md)에 있고,
코드는 `lib/analytics/`에 모여 있다.

## 기록 템플릿

새 파일을 만들 때 아래를 복사해서 채운다. 네 항목을 전부 채우는 게 핵심이다 —
**관측만 적고 다음 가설이 없으면 반복이 아니다.**

```markdown
# N차 검증 (YYYY-MM-DD ~ YYYY-MM-DD)

측정 기간: N일 · 방문자 N명

## 1. 관측

숫자만 적는다. 해석은 다음 칸에서 한다.

| 가설 | 기준 | 실제 | 판정 |
|---|---|---|---|
| H1 온보딩 완료율 | 60% | ?% | 달성 / 미달 |
| H2 선택 항목 입력률 | 30% | ?% | 달성 / 미달 |
| H3 체류시간 (프로필 유/무) | 유 > 무 | ?초 / ?초 | 달성 / 미달 |
| H4 후기 작성 전환율 | 15% | ?% | 달성 / 미달 |
| H5 구매 이탈률 | 25% | ?% | 달성 / 미달 |

빈 화면 사유 분포:
- no_profile: ?회
- no_reviews: ?회
- insufficient_recommendation: ?회

## 2. 해석

왜 그 숫자가 나왔다고 보는가. 근거 없는 추측이면 추측이라고 적는다.

## 3. 다음 가설

무엇이 참이라면 이 숫자가 개선되는가. 검증 가능한 형태로 쓴다.

## 4. 바꿀 것

다음 주기에 실제로 바꿀 것 하나. 여러 개를 동시에 바꾸면 무엇이 효과였는지 알 수 없다.
```
